01What it is

Meal Explorer is a recipe browser built around TheMealDB, a free public API. It has three jobs: let someone browse and search recipes, filter them by category, and open a full recipe with scalable ingredient quantities.

The app follows the course's plain StatefulWidget + setState style deliberately — no Provider, no service layer, no data-model classes. Every screen fetches its own data with http.get and decodes it with jsonDecode, the same pattern used in the ChatPage/News-App examples from the slides.

Why this matters for the walkthrough

If asked "why no Provider," the honest answer is scope: favorites only need to be shared between four screens for one session, which a single List passed down through constructors handles without extra machinery — the same "lift state up" pattern the slides use for theming before introducing Provider.

02File layout

Six files, flat in lib/, one per screen plus the entry point. No models/ or services/ folders — API responses are used directly as Map<String, dynamic>.

lib/ main.dart — entry point + bottom-nav shell + favorites state home_screen.dart — search bar, category chips, meal grid search_screen.dart — text search + category filter chips categories_screen.dart — full category grid favorites_screen.dart — saved meals list meal_detail_screen.dart — recipe, servings, video link

Every screen widget that needs favorites declares three required constructor parameters: favoriteMeals, isFavorite, and toggleFavorite. MainScaffold in main.dart is the only place that owns that state; everyone else receives it.

03Screens

Four bottom-nav destinations, plus the detail screen reached from any of them.

Home

home_screen.dart

Loads the category list and, by default, all meals via an empty search.php?s= query. Tapping a category chip re-fetches through filter.php instead. Grid cards carry a heart button that calls toggleFavorite directly.

Search

search_screen.dart

Opened from Home's search bar or from a Categories tap (via an optional initialCategory parameter). Runs search.php?s={query}, then narrows the already-fetched results client-side against each meal's strCategory field when filter chips are active.

Categories

categories_screen.dart

A grid built from list.php?c=list. Tapping a tile pushes Search pre-filtered to that category.

Favorites

favorites_screen.dart

Pure presentation — reads straight from the favoriteMeals list passed down from MainScaffold, no network call of its own.

Meal detail

meal_detail_screen.dart

Fetches the full recipe via lookup.php?i={id}, builds the ingredient list from the API's 20 numbered strIngredientN / strMeasureN fields, and drives a servings stepper that rescales quantities live. A "Watch recipe" button opens strYoutube via url_launcher when present.

04API endpoints

Four TheMealDB endpoints cover the whole app. There's no single "list every meal" endpoint, so an empty search query is used as the accepted workaround for that.

PurposeEndpointUsed in
Search by name search.php?s={query} Search screen; also Home with an empty query, standing in for "all meals"
List categories list.php?c=list Home's chip row, Categories screen
Filter by category filter.php?c={category} Home, when a category chip is selected
Full meal lookup lookup.php?i={id} Meal detail screen

final url = selectedCategory == 'All'

    : Uri.parse('https://www.themealdb.com/api/json/v1/1/filter.php?c=$selectedCategory');

final response = await http.get(url);
if (response.statusCode == 200) {
  final data = jsonDecode(response.body);
  setState(() { meals = data['meals'] ?? []; });
}

05How data flows

Favorites are the only state shared across screens, and they live in exactly one place.

  1. MainScaffold (in main.dart) holds List<Map<String, dynamic>> favoriteMeals as instance state.
  2. It builds the four tab screens each turn, passing favoriteMeals, an isFavorite(id) lookup function, and a toggleFavorite(meal) callback into every constructor.
  3. Screens that push a child screen (Home → Search or Detail, Categories → Search, Search/Favorites → Detail) simply forward the same three parameters along — nothing is re-derived.
  4. Calling toggleFavorite anywhere calls setState back up in MainScaffold, which rebuilds the tree and every heart icon updates together.

Favorites are in-memory only — they reset when the app restarts. That was a deliberate scope call for this build, not an oversight (see §07).

06Servings math

TheMealDB doesn't return structured quantities — just free-text strings like "1/2 cup" or "2". The detail screen does best-effort scaling rather than skipping the feature entirely.

How scaleMeasure() works

  1. A regex, ^(\d+\/\d+|\d+\.\d+|\d+)\s*(.*)$, pulls the leading number (plain, decimal, or a simple fraction) off the front of the measure string.
  2. Fractions are converted to a decimal (1/2 → 0.5).
  3. The value is multiplied by servings / 4 — TheMealDB's recipes are written for 4 servings by default.
  4. The result is trimmed to a clean decimal and reattached to whatever text followed the number (e.g. "cup").
  5. If the string has no leading number at all — "to taste", "pinch" — the regex simply doesn't match and the original text passes through unchanged.
meal_detail_screen.dartexcerpt
// 100 g at 4 servings → 125 g at 5 servings
final scaled = value * servings / 4;
var scaledText = scaled.toStringAsFixed(2);
// trims trailing .00 / trailing zero before display

Verified live: at 4 servings Flan calls for 100 g sugar; bumping to 5 servings recalculates to 125 g automatically.

07Known limitations

Worth naming these up front — it reads as intentional scoping, not gaps you missed.

  • Favorites don't persist. No shared_preferences yet, by design — the brief called for in-memory only.
  • Search's quick-filter chips are a fixed set (Seafood, Chicken, Vegetarian, Pasta, Dessert), matching the original mockup. Opening a different category from the Categories tab — say, Beef — still filters correctly, but that category won't appear as a highlighted chip in the row.
  • Servings scaling is text-based, not unit-aware. It scales the number; it doesn't convert cups to grams or round to sensible cooking fractions.
  • "All meals" is simulated via an empty search.php?s= query, since TheMealDB has no dedicated list-everything endpoint.
  • "Watch recipe" only appears when TheMealDB actually supplies a strYoutube link — many meals don't have one.

08Anticipated questions

A quick rehearsal for the walkthrough.

Why didn't you use Provider or a service layer?
The assignment asked for the course's plain StatefulWidget/setState style. Favorites are the only cross-screen state, and passing them through constructors — the pattern used for theme-switching earlier in the slides — is enough for that scope without pulling in a package.
Why is there a Map<String, dynamic> everywhere instead of a Meal class?
Same reasoning: the course examples (Universities app, dBooks homework) work directly off decoded JSON maps rather than typed models. It keeps each screen self-contained and matches what was taught.
How does the servings stepper actually change the numbers?
See §06 above — a regex extracts the leading quantity from each ingredient's measure string and re-scales it by servings ÷ 4 on every rebuild.
What happens if the API call fails?
Each screen tracks its own isLoading and errorMessage state and shows a spinner, an error message, or an empty-state message — never a blank screen or an unhandled exception.
